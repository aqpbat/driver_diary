# Дневник смен водителя — план реализации

Статус: этапы 1 и 2 готовы (репозиторий, данные, домен, хранилище на PostgreSQL, HTTP API — всё с тестами). Dockerfile и деплоя ещё нет, `mobile/` — чистый шаблон Flutter.

## 1. Решения

| Тема | Решение | Почему |
|---|---|---|
| Бэкенд | Go 1.26.8, стандартная библиотека + один модуль — драйвер PostgreSQL `pgx/v5` | `net/http` с Go 1.22 умеет `GET /path/{param}`, роутер не нужен. `pgx` — чистый Go, сборка остаётся `CGO_ENABLED=0`. Локально стоит Python 3.9.6 — слишком старый |
| Клиент | Flutter 3.47.5 / Dart 3.13.4 (уже в `mobile/`), платформы Android, iOS, Web | Шаблон уже создан; Web-сборка даёт демо-ссылку без установки приложения |
| Хранилище | PostgreSQL 18.6: локально — сервис `db` в compose, на Railway — управляемый Postgres. Начальные данные из `api/data/trips.json` заливаются в пустую базу | Данные переживают рестарт и деплой; защита от дублей — первичный ключ, работает и при нескольких репликах API; ограничения `CHECK` в схеме — вторая линия проверки после `trip.Validate` |
| Деньги | Целые числа (тенге), без `float` | Сводка — это суммы; с плавающей точкой будут копеечные расхождения |
| «День» | Локальная дата **начала** поездки в часовом поясе `APP_TZ` (по умолчанию `Asia/Almaty`, UTC+5) | Поездка 23:50–00:20 относится к дню начала; поездка, присланная с другим смещением, приводится к `APP_TZ` |
| «На руки» | `amount − commission` | Единственная трактовка, которая следует из данных |
| Идемпотентность | Клиент генерирует `id` (UUID v4) один раз на форму и шлёт его при каждом повторе | Не нужен отдельный заголовок; ключ совпадает с `id` из исходного формата |
| Дизайн | Своя дизайн-система поверх `WidgetsApp`, без `package:flutter/material.dart` | Требование «без Google Material» |
| Архитектура клиента | Clean Architecture с делением по фичам (feature-first), состояние — `flutter_bloc` | См. раздел 3.1. `flutter_bloc` зависит только от `widgets`, с отказом от Material не конфликтует |

### Развилки, которые стоит подтвердить

1. **Поля ввода.** Без Material нет готового `TextField`. Предлагаю взять `CupertinoTextField` с обнулённым оформлением как «движок» ввода (курсор, выделение, клавиатура), а весь внешний вид рисовать своими компонентами. Альтернатива — писать на голом `EditableText`: чище по идее, но это день работы на ручки выделения и меню копирования.
2. **Комиссия в форме.** Отдельное поле с подстановкой 15 % от суммы (в примере 360/2400 и 225/1500 — ровно 15 %), которое можно исправить. Сервер комиссию не вычисляет, только проверяет.
3. **Демо.** Flutter Web на GitHub Pages + API на Railway. Если демо не нужно — блок E5 выпадает.

## 2. Контракт API

Базовый путь `/api/v1`. Все ответы — JSON. Время — RFC 3339 со смещением, в ответах всегда в `APP_TZ`.

| Метод | Путь | Ответ |
|---|---|---|
| `GET` | `/healthz` | `200 {"status":"ok"}`; база недоступна — `503` |
| `GET` | `/api/v1/days` | `200 {"days":[{"date":"2026-10-01","trips_count":2}]}` — по возрастанию даты |
| `GET` | `/api/v1/days/{date}` | `200 {"date","summary","trips"}`; день без поездок — `200` с нулевой сводкой и пустым списком; кривая дата — `400` |
| `POST` | `/api/v1/trips` | `201` — создана; `200` — такая же уже есть (повтор); `409` — `id` занят другой поездкой; `422` — не прошла проверку (в том числе неверный тип или лишнее поле); `400` — не JSON; `413` — тело больше 64 КБ |

Сводка:

```json
{
  "trips_count": 2,
  "revenue": 3900,
  "commission": 585,
  "net": 3315,
  "by_payment": {
    "cash": {"trips_count": 1, "revenue": 1500, "commission": 225, "net": 1275},
    "card": {"trips_count": 1, "revenue": 2400, "commission": 360, "net": 2040}
  }
}
```

Ошибка (единый формат):

```json
{"error": {"code": "validation_failed", "message": "...", "fields": {"end": "must be after start"}}}
```

Проверки при добавлении:

- `id` — обязателен, непустой, до 64 символов;
- `start`, `end` — RFC 3339 со смещением; `end > start`;
- `amount > 0`; `0 ≤ commission ≤ amount`; оба — целые;
- `payment` ∈ `cash`, `card`;
- неизвестные поля в теле — ошибка (`DisallowUnknownFields`), тело не больше 64 КБ.

«Та же поездка» = совпадают `id`, моменты начала и конца (сравнение моментов, а не строк), сумма, оплата, комиссия.

### 3.1 Архитектура клиента

Каждая фича — три слоя, зависимости направлены внутрь, к `domain`:

| Слой | Что лежит | От чего зависит |
|---|---|---|
| `domain` | Сущности, интерфейсы репозиториев, use case'ы (`GetDay`, `GetDays`, `AddTrip`), правила проверки формы | Только Dart и `core/domain`, `core/error`. Никаких `flutter`, `http`, `bloc`, JSON |
| `data` | Удалённый источник данных, DTO с `fromJson`/`toJson` и переводом в сущности, реализации репозиториев | `domain`, `core/network` |
| `presentation` | Bloc/Cubit, страницы, виджеты | `domain`, `core/design`. Не знает про `data` |

Правила:

- Виджет общается только с Bloc; Bloc — только с use case'ами; use case — с интерфейсом репозитория. Виджет не вызывает репозиторий, Bloc не знает про HTTP и JSON.
- Фичи не импортируют друг друга. Общее выносится в `core/`. Связь «добавили поездку → обновить день» идёт через результат закрытия формы, который обрабатывает страница дня.
- Исключения не выходят из слоя `data`: репозиторий превращает их в `Failure` (сеть, проверка с ошибками по полям, конфликт `id`, неизвестная) и возвращает `Result<T>` — свой `sealed`-класс, без `dartz`.
- Зависимости создаются в одном месте (`app/`) и передаются через конструкторы и `RepositoryProvider`/`BlocProvider`. Без `get_it` и глобальных синглтонов.
- Состояния и события Bloc — `sealed`-классы с `Equatable`; в `build` — исчерпывающий `switch`.
- `DayBloc` (события: запуск, выбор дня, обновление) — при быстром листании дней ответ на устаревший запрос отбрасывается (`restartable()` из `bloc_concurrency`).
- `AddTripCubit` создаёт `id` поездки один раз в конструкторе и хранит его в состоянии — повторная отправка идёт с тем же `id`.
